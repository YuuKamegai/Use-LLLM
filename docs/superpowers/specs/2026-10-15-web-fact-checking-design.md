# APIキー不要のWeb検索・事実確認

日付: 2026-10-15（Asia/Tokyo）

状態: 2026-10-15に本文承認済み。実装・独立レビュー指摘修正・262テスト検証済み。元の作業場所への統合待ち。

## 1. 目的と承認された挙動

Use-LLLMのOllamaとAzure OpenAIの双方から、一般Web検索と公開ページ本文取得を利用する。
ユーザーが毎回「検索して」と指定しなくても、時事情報、最新仕様、変動する数値、専門的で
不確かな内容ではLLMが検索し、本文を確認して、根拠にリンクを付けた回答を生成する。
翻訳、文章の書き直し、単純な計算など、外部情報が不要な質問では検索しない。

ユーザーが設定でWeb検索を一度有効化すると、内蔵の検索・本文取得は個別承認なしで動作する。
無効化すると両ツールはLLMに公開されず、直接の実行要求も拒否される。
APIキー、別の検索サーバー、ブラウザー拡張の準備を必須にしない。

ChatGPTと同一の検索品質やモデル判断を保証するという意味ではなく、
「必要性を判断 → 検索 → 本文確認 → 出典付き回答」という利用体験を目指す。

## 2. 現在の実装との接続

- `core/settings_store.py`: AI接続とMCP設定をJSONへ保存している。
- `core/mcp_registry.py`: ツール一覧、名前解決、実行判定、引数検証、実行結果を共通化している。
- `general/agent_loop.py`: 両プロバイダーで同じツール実行ループを使う。
  ストリーミング、非ストリーミング、承認後の再開の各経路が存在する。
- `core/tool_catalog.py`: ツール説明を要約し、必要時に詳細説明を取得する。
- `general/api.py`: 設定を適用するとモデルクライアントとレジストリを構築し直す。
- `general/static/index.html`, `app.js`, `i18n.js`: 設定パネルと日英表示を実装している。

現在の`allow_network`は通信を許可する設定であり、外部通信の個別承認は省かない。
この一般設定を緩めることでWeb自動実行を実現してはならない。

## 3. 採用する構成

### 3.1 内蔵Webツール

`src/use_lllm/web/`に検索、本文取得、共通の結果型、ツールアダプターを置く。
LLMにはMCPと同じfunction schemaと`MCPToolResult`で公開するが、別プロセスは起動しない。
Use-LLLM側に組み込み、ms-data-parser側の変更は不要とする。

レジストリのラッパーを追加し、信頼済みの内蔵ツール2件だけを扱う。
通常のMCPツールの一覧・判定・呼び出しは既存レジストリへ委譲する。
ツール名文字列や外部サーバーのannotationsだけで内蔵ツールと判定しない。
`web`という既存MCPサーバー名がある状態では有効化を拒否し、名前衝突をUIに示す。

ラッパーはツール一覧、`get_tool`、サーバーinstructions、判定、呼び出し、状態、
セッション接続世代、セッション終了・全接続終了という既存の利用契約を維持する。
内蔵Webツールは状態復旧の前提を持たず、MCP接続を開く必要はない。
`GeneralRuntime`が設定に応じて通常レジストリを包み、両LLMへ同じツールを渡す。

### 3.2 検索と本文抽出

検索は`ddgs`の`DDGS.text`を利用する。初期バックエンドは明示的に`duckduckgo`を指定する。
`auto`を使って、ユーザーに説明していない検索先へ自動拡散させない。
バックエンドが使えない場合、別サービスへの黙った切替はせず、検索失敗を返す。

本文取得は独立したHTTP取得処理と`trafilatura`のHTML本文抽出を組み合わせる。
`DDGS.extract`は任意URL取得の制御をUse-LLLM側で統一できないため利用しない。
HTMLとプレーンテキストを対象とする。検索結果のページを自動で一括取得せず、
LLMが根拠確認に必要なURLを選んで`read_page`を呼ぶ。

依存関係は`pyproject.toml`と`uv.lock`へ記録する。採用版のAPIと対応Pythonを確認し、
Windowsの実行環境でimport・検索・抽出を確認する。依存の取得先は通常のパッケージレジストリ。

## 4. ツール契約

### `web::search`

- 入力: `query`（1〜500文字）、`max_results`（1〜10、既定5）。
- 日本語と英語の検索を扱い、既定regionは`jp-jp`、SafeSearchは`moderate`とする。
- 出力: `status`, `query`, `backend`, `retrieved_at`, `results`, `error`。
- 各結果: `title`, `url`, `snippet`。タイトル300文字、概要1000文字まで。
- URLを正規化して重複を除く。非HTTP(S)や内部宛ての結果は除外する。
- 出版日が取得できない場合は推定しない。取得日時を出版日として扱わない。
- `ok`、`no_results`、`error`を区別する。ライブラリが検索失敗と0件を区別できない例外を
  返す場合は、保守的に`error`とし、該当情報が存在しないとは主張しない。

### `web::read_page`

- 入力: `url`（HTTP(S)、最大2048文字）。
- 出力: `status`, `requested_url`, `final_url`, `title`, `text`, `retrieved_at`,
  `truncated`, `error`。公開日が確実に抽出できた場合のみ`published_at`を含める。
- 取得本文は最大12,000文字。省略は`truncated=true`で明示する。
- robots.txtによる拒否、ログイン必須、CAPTCHA、取得失敗、本文なし、非対応形式を区別する。
- HTMLのscript、フォームなどを実行しない。取得テキストを非信頼の資料として扱い、
  ページ内の命令でツール実行方針やユーザーの指示を変更しない。

両ツールはread-onlyかつ外部通信として分類する。
エラーは構造化した結果と`is_error`へ反映し、成功として履歴へ混ぜない。
`error.code`は`timeout`, `rate_limited`, `search_failed`, `fetch_failed`,
`blocked_url`, `robots_denied`, `unsupported_content`, `content_too_large`, `empty_content`を使う。
接続先の応答から確実に判定できないCAPTCHAやレート制限は`fetch_failed`等にとどめ、断定しない。

## 5. 自動検索と回答方針

Web有効時だけ、両LLMに共通の検索instructionsを渡す。

1. ユーザーの「検索しない」「指定資料だけ」の条件を優先する。
2. 明示的な検索要求、最新情報、変動する事実、検証の必要な不確かな内容で検索する。
3. 質問の要点を検索語へ変換する。会話全文、ローカルファイル本文、サンプル名、
   APIキーなどを自動で検索語へコピーしない。
4. 公式資料・一次資料を優先し、結論に必要なページ本文を読む。
5. 情報が食い違う場合は、日付・対象条件を比べて違いを説明する。
6. 確認した主張の近くにMarkdownの出典リンクを付ける。
   取得結果にないURLや確認していない本文を根拠として作らない。
7. 検索失敗や確認不能では「確認できなかった」と述べ、推測と区別する。

検索要否はモデルが判断する。初版では全質問を別LLMで分類する前処理や、
すべての回答後に追加検索する処理を入れない。モデルごとの差は評価で把握する。
ツール呼び出し非対応モデルや、指示を守らないモデルで同等の挙動を保証しない。

1ユーザー発話からの実行上限は検索4回、本文取得6回とする。
既存の20ステップ上限も維持する。承認後の再開でWeb回数をリセットしない。
上限到達は明示的なエラーにして、追加呼び出しを繰り返さず取得済み情報で回答するよう指示する。

## 6. 通信・リソース制限

- 本文取得はHTTP(S)の80/443ポートのみ。URLのユーザー名・パスワードを拒否する。
- localhost、private、loopback、link-local、multicast、予約アドレス、IPv4-mapped IPv6、
  非公開DNS解決先を拒否する。複数IPの一つでも非公開なら拒否する。
- DNS確認後に別のIPへ接続しないよう、検証済みIPへの接続を固定する。
  元ホスト名のHost/SNIと証明書検証は維持する。環境プロキシによる検証迂回を許さない。
- リダイレクトは最大3回。自動追従せず、遷移先ごとにURL/DNS/接続IPを検証する。
- robots.txtは同じ取得制御で確認する。404は規則なし、拒否規則や確認失敗では本文取得を止める。
- 応答はストリームで上限2MiB（展開後も検査）。ヘッダーのサイズ申告だけを信用しない。
- 検索は1呼び出し30秒、本文取得はrobots・リダイレクト・DNSを含め合計30秒まで。
  同期検索はイベントループ外で実行し、同時実行数を制限する。
  タイムアウト後も動くワーカーが無制限に増えない実装とテストを必要とする。
- SSL検証を無効にしない。Cookie、ユーザーのログイン情報、LLM APIキーをページ先へ送らない。
- 検索エンジンには生成した検索語、ページ先には対象URLを送ることを設定欄で説明する。

## 7. 設定とUI

`Settings`へ`web_search_enabled: bool = False`を追加する。
旧settings.jsonには値がなくても読み込め、オフとして扱う。
この実装タスクで、ユーザーの実際の保存済み設定を自動でオンにはしない。

「接続と設定」の上部に、MCPサーバー編集とは別の「Web検索」セクションを追加する。

- 「Web検索と公開ページ取得を有効化」スイッチ。
- 「APIキー不要 / DuckDuckGo」とオン・オフ状態を表示。
- 「有効時はAIが必要に応じて検索し、検索・ページ取得を個別確認なしで実行」と説明。
- 一般MCP設定の`allow_network`とは独立していることを明確にする。
- 日英表示に対応する。

設定参照は既存`GET /api/settings`のレスポンスに追加し、
更新用`PUT /api/web-search`は`{enabled: boolean}`のみ受け取る。
既存のCSRF・loopback保護とセッション実行中の設定変更ルールに従う。
有効な場合は既存Connected tools一覧にも2ツールを表示し、セッション単位の無効化を尊重する。

検索中・ページ確認中は既存SSEの`tool_started`/`tool_result`を使って短く表示する。
検索語、取得URL、結果、失敗を既存のツール履歴へ保存する。
回答の出典は既存Markdownリンク描画で表示し、別の引用記法を導入しない。

## 8. 変更範囲と検証

追加先: `web/`の検索・取得・結果型・内蔵レジストリアダプター。
変更先: 設定ストア、GeneralRuntime/API、共通エージェントのinstructionsと回数制限、
設定UI・日英辞書・必要なCSS、依存関係、README、対応するtests。
既存MCPポリシーの分類規則、ms-data-parser、実データ、既存チャット本文は変更対象外。

受入条件:

1. 旧設定の読込・オン/オフの保存・再読込ができる。無効時はWeb通信もツール公開もない。
2. 有効時は内蔵2ツールだけが個別承認不要。名前衝突や偽装した外部MCPは権限を得ない。
3. 検索成功、空結果、制限、例外、タイムアウトを区別し、日本語クエリを扱える。
4. 本文抽出・省略・取得日時・最終URLを検証できる。
5. URL/DNS/IP検証、リダイレクト、robots、容量・時間・回数上限に回帰テストがある。
6. ストリーミング・非ストリーミング・承認後再開で同じ設定・制限が効く。
7. OllamaとAzureの偽クライアントで検索→本文→出典付き回答の流れを検証する。
   単純な翻訳で不要な検索をしないケースと、検索失敗を回答に反映するケースも含む。
8. UIでWeb設定と進行状況を視認し、既存MCP設定・ツール一覧が壊れていないことを確認する。
9. 決定的な自動テストはネットに依存させず、通信とモデルは置き換える。
   公開情報のみの実検索・本文取得を別のsmoke検証として記録する。
10. 実LLMの自発的検索と出典の正確さは自動テストとは別に評価する。
    使用モデル・接続先・検索語・取得URLを記録し、未実施なら未確認と報告する。
    料金のかかる実モデル呼び出しや起動中アプリの再起動は、実行範囲を明示して扱う。

## 9. 初版の対象外

ログイン済みブラウザー操作、フォーム送信、購入、ブラウザーの履歴やCookieの利用、
JavaScript必須ページの描画、PDF抽出、画像・動画検索、検索APIの課金キー設定、
SearXNGの運用、全回答の事後検証、論文コーパスへの自動取り込み。
